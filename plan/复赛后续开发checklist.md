# 澳门 StoryWalk 复赛后续开发 Checklist

> 本清单依据 `report ver2.docx`、当前仓库代码和现有计划交叉整理，面向技术方案确认与复赛开发排期。
>
> **当前基线（2026-08-19）**：Web MVP 的主流程已经具备：四语入口、登录、偏好采集、路线生成与调整、地图与签到、AI 导览/问答、拍照识别、明信片、个人中心，以及一条完整的 StoryWalk V4 故事线。前端生产构建通过；后端全量测试尚待启动 Postgres 后验证。

## 0. 先完成环境与验收基线（P0）

> 不完成这一节，不应把后续改动视为“已交付”。

- [ ] 启动本地依赖：`docker compose up -d --build`。
- [ ] 确认服务健康：Postgres、backend、seed 均正常；记录 `docker compose ps` 输出。
- [ ] 使用专用 Conda 环境执行后端测试：
  ```bash
  conda run -n qwenpaw bash -lc 'cd backend && python -m pytest -q -p no:cacheprovider'
  ```
- [ ] 对失败分类并留档：环境/数据迁移/测试预期/真实代码缺陷；不要把数据库未启动造成的连锁失败当成代码失败。
- [ ] 运行 `cd frontend && npm run build`，作为每次合并前的最低前端门槛。
- [ ] 完成一次真机验收（360、375、390、412、430px）：正常路线、StoryWalk、图片识别失败、Agent 失败、无定位授权五条路径。
- [ ] 建立一份可重复的“复赛 Demo 检查表”：账号、密钥、QwenPaw Console、地图 Key、TTS/OSS、网络故障降级、演示数据和录屏备份均可用。

**技术方案待定**

- [ ] 决定 CI 运行模型：GitHub Actions 是否启动 PostGIS service container，还是使用独立测试数据库。
- [ ] 决定本地开发环境唯一入口：Docker Compose 为主，还是 Conda + 本地 Postgres 为主；避免团队成员使用不同且未记录的环境。
- [ ] 将 `qwenpaw` Conda 环境的依赖导出为可复现清单（例如 `environment.yml` 或受控 requirements lock），不依赖个人机器已有包。

## 1. 账户、权限与数据生命周期（P0，上线前必须完成）

**现状**：故事会话已做所有权校验；Trip、明信片和部分用户偏好仍存在按资源 ID 直接访问/操作的路径，尚未统一执行 JWT 所有权校验。

- [ ] 为 Trip API 添加 `require_user_id`，并在创建、查询、签到、进度查询时验证 `trip.user_id == current_user_id`。
- [ ] 为明信片的创建、列表、图片读取、删除添加“Trip 所有者/明信片所有者”校验。
- [ ] 将用户偏好更新和收藏接口改为 `/users/me/...` 或校验 URL 中 `user_id` 与 JWT subject 一致。
- [ ] 为越权读取、越权修改、越权删除分别补 API 测试，预期均为 `401` 或 `403`。
- [ ] 增加 `GET /api/v1/users/me/export`：可导出个人资料、偏好、行程、签到、反馈、明信片元数据；明确不包含不必要的原始图片。
- [ ] 增加 `DELETE /api/v1/users/me`：级联/事务性删除账号及全部关联数据，返回可审计的删除结果。
- [ ] 明确信息保留周期：审计日志、上传的脱敏图片、明信片图片、故事会话分别保留多久，过期任务如何运行。
- [ ] 增加后台/定时清理任务，自动删除到期的图片与相关持久化记录。

**验收**

- [ ] 用户 A 无法通过猜测 ID 获取、签到、删除用户 B 的 Trip 或明信片。
- [ ] 删除用户后，以原 Token 和资源 ID 均不可再访问该用户数据。
- [ ] 导出内容与数据库中该用户的可见数据一致，且不泄露其他用户数据。

## 2. AI、QwenPaw 与可靠降级（P0）

**现状**：路线、意图、偏好引导、拍照、讲解、审核的 Agent 代码与 Skill 均存在，但功能开关默认关闭，是否真正使用 Agent 取决于现场 QwenPaw/模型/密钥配置。

- [ ] 在 QwenPaw 环境中核对并记录各 Agent ID、模型、挂载 Skill、工具权限和版本：intent、preference-guide、route、guide、photo、reviewer、scene。
- [ ] 配置并验证所有 Agent 开关；对每个接口记录 `source=agent` 的实际调用证据。
- [ ] 为每个 Agent 编写至少一组成功、一组低置信、一组超时/服务失败的端到端验收案例。
- [ ] 统一 Agent 输出 schema；后端必须校验、记录版本，并在解析失败时退回确定性规则/保守文案。
- [ ] 将 `source-attribution`、`anti-sycophancy`、`content-safety-review` 纳入真实调用链，而不只保留 Skill 文件。
- [ ] 加入提示注入、越权工具调用、虚构史实、错误迎合、敏感内容等回归测试。
- [ ] 为每次 AI 调用保留去标识化审计信息：模型、Prompt 版本、耗时、成功/失败、审核结论；禁止保存原始敏感图片或完整私人对话。
- [ ] 准备“无 QwenPaw/无网络/无 TTS/无图像模型”演示降级剧本，确保主流程不被外部服务中断。

**技术方案待定**

- [ ] 确定是否继续采用“后端编排 + 专用 Agent + 规则执行 + Reviewer”受控模式；复赛不建议改成 Agent 自主互相调用，除非能提供可靠性与成本证据。
- [ ] 确定 RAG 策略：pgvector 作为正式检索库，还是保留当前本地资料/关键词降级；定义索引更新与来源审核流程。
- [ ] 确定模型成本、超时、并发、限流与缓存上限，写入部署配置。

- [ ] 路线结果页稳定展示“为什么推荐/为什么调整/哪些信息来自实时信号”。

- [ ] 将“每道谜题不得泄露的内容”写入故事 Agent 上下文；目前通用防剧透规则需要进一步细粒度化。
- [ ] 建立全量视觉资产版权台账：文件、作者/来源、许可证、授权范围、到期日、购买或授权凭证、替代方案。
- [ ] 补齐照片车牌检测与模糊；保持 EXIF/XMP 移除和人脸模糊的现有流程。
- [ ] 写清楚 QwenPaw、地图、TTS、图像模型等第三方的数据处理地点、用途、留存和删除机制。
- [ ] 为团队填入内容更正、隐私安全、用户投诉三类责任人及处理流程。

**验收**

- [ ] 故意输入错误历史断言时，系统会纠正/保守说明并展示来源，不会迎合。
- [ ] 上传不可识别图片时，系统只返回“未能确定 + 重拍/手选”，不自动跳转到错误讲解。
- [ ] 任一公开故事资源均可在台账中查到授权状态。

## 4. 路线、位置与实时信息（P1）

**现状**：路线、步行路径、GPS 附近识别、位置签到与模拟到达已具备；已实现澳门气象局天气和旅游局活动日历的轻量实时上下文。它们不是完整交通/实时客流/安全导航系统。

- [ ] 明确演示与产品文案：当前是“辅助导览和建议”，不是权威安全导航。
- [ ] 加入道路封闭、施工风险、无障碍状态、官方景点开放时间等可核验信号；每一类信号都需来源、更新时间和不可用降级。
- [ ] 将天气/活动信息从提示性上下文升级为可解释的路线约束；避免无依据地断言“人流拥挤”。
- [ ] 为常规路线实现可配置的 GPS 围栏、精度阈值、连续位置判定与防重复触发。
- [ ] 明确故事模式的策略：保留主动“我已到达”用于远程演示，还是增加 GPS 验证后解锁；两种模式都必须对用户透明。
- [ ] 做一次澳门实地走测：定位成功率、提示频率、签到误差、步行路段正确性、语音可用性与用户干扰度。
- [ ] 扩充路线候选与“相似点替换”能力，确保加点、减步行、摄影/亲子/美食需求不会造成跨区绕路。

### 9.2 策划书明确列出的功能与内容扩展

- [ ] **POI 与文化知识库扩展**：覆盖澳门半岛、氹仔、路环；补充历史建筑、博物馆、美食店铺、特色街区、图片、语音、来源和文化关联。
- [ ] **多语言导览深化**：从四语入口升级为四语讲解内容、TTS、不同文化背景的表达；补充亲子、教育、一般游客等叙事风格。
- [ ] **实时资讯服务**：天气、公共交通、景点开放时间、节庆活动、人流/拥挤预测，并让这些信息能被可解释地用于路线调整。
- [ ] **长期偏好模型**：复用历史路线、兴趣、步行习惯、停留时长、常用语言和互动风格；需要先通过用户同意、可查看、可修改、可删除的隐私设计。
- [ ] **多 Agent 协同增强**：任务分解、上下文共享、记忆同步、工具调用、动态工作流编排；应先用可控编排的评测证明收益，再扩大自主性。
- [ ] **定位真实性增强**：结合精度、连续位置、地理围栏和签到时间；保留演示用模拟到达，但不得把它表述为严格实地认证。
- [ ] **剧本奖励联动**：故事奖励、结局补记与普通旅行明信片自动关联，形成“走完故事—留下纪念”的闭环。

### 9.3 策划书中的产品化承诺（不建议挤占复赛主线）

- [ ] 微信小程序：地图/定位、微信登录、界面适配、本地缓存与离线能力。
- [ ] iOS/Android：实时语音导览、地理围栏、旅行记录、社交分享；AR 互动属于更长期方向。
- [ ] 开放式文旅 Agent 平台：将澳门数据层、能力层、Agent 层和交互层抽象为可迁移的城市框架。

**执行约束**：不得以“故事策划已完成”替代功能交付，也不得以占位页面替代完整故事。三条线应共享同一套数据契约、状态机、谜题组件、来源/虚构边界、素材管理和验收方法；这样可以让后两条线复用既有 V4 能力，而不是重复开发三个彼此割裂的系统。

### 10.1 每条故事线的 RACI 规则

| 工作项 | 故事负责人 | 横向主责人 | 其他两人 |
| --- | --- | --- | --- |
| 范围、路线、章节与验收用例 | A（最终负责） | C（技术约束） | R（共同评审） |
| 史料、来源、虚构边界、POI 数据 | A（内容确认） | R（张弘毅执行/审核） | C（交叉核验） |
| 后端数据、状态机、测试 | A（验收） | R（张弘毅实现/审核） | C（接口评审） |
| 前端页面、地图、谜题、素材降级 | A（验收） | R（陈思睿实现/审核） | C（移动端走测） |
| Agent、审核、审计、外部服务降级 | A（验收） | R（肖懿宣实现/审核） | C（失败案例测试） |

> 说明：`A` = 对结果最终负责；`R` = 直接实施/审核；`C` = 必须参与评审。无论故事归谁，涉及后端、前端、Agent 的公共能力必须由对应横向负责人把关，避免三个故事包各自形成不兼容实现。

### 10.3 让工作量真正相同的执行规则

- [ ] 每人每周同时关闭：至少 1 个故事内容/数据任务、1 个技术实现任务、1 个可验证验收任务。
- [ ] 每个 PR 必须关联一个故事线、一个横向能力和一条验收用例；禁止只提交素材或只提交文档却没有可运行变化。
- [ ] 每条线每周至少一次三人走查：故事负责人演示，另两人分别从“事实可信度”和“手机操作体验”提出阻塞问题。
- [ ] 三条线各自使用相同的完成定义：数据、后端、前端、Agent、素材、测试、真机验收均完成才可勾选。
- [ ] 澳门半岛现有代码较多，因此肖懿宣除主线负责人外，还承担三条线的整合、Agent 与最终 Demo 工作，用以平衡氹仔/路环从零创建内容的投入。
- [ ] 张弘毅和陈思睿不能只做本线：前者对三线的数据/后端标准负责，后者对三线的前端/移动端标准负责；这样三人的贡献均会反映在共同底座和各自主线中。

1. **第 1 周：** 环境/测试基线、资源级权限、Agent 现场验收；冻结三条线的统一故事数据契约与验收标准。
